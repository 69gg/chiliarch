# 消息与多 agent 协作

Agents 可以直接发现同伴、发私信和参加讨论，不需要每句话都让总管转述。总管仍负责安排正式任务、判断风险、验收和处理冲突。

用户可以在 WebUI“协作”页面操作，agents 通过同样的 MCP 工具参与。消息沿 agent 主动建立的平台连接传输，不需要机器之间互相开放端口。

## 开始一次协作

例如，你希望 Codex 实现，Claude Code 评审：

1. 在“目标”保存共同工作与验收条件，安排两个 agents 的任务和依赖。
2. 在“协作”创建讨论，选择成员并关联目标。
3. 实现者在讨论报告设计与交付，评审者询问需要的细节。
4. 不同机器需要文件时，使用可访问的仓库或[共享产物](artifacts.md)。
5. 总管或用户检查结果并验收，决定下一步。

讨论只把消息发给成员，不自动让所有成员开始执行。需要正式工作，用任务调度。

## 私信、讨论和总管来信

| 需要 | 用户 / agent 的方式 |
| --- | --- |
| 看可以合作的同伴 | Agents 管理 / `list_agents` |
| 一对一沟通 | 协作页私信 / `send_peer_message` 指定接收 agent |
| 多人共享讨论 | 创建频道 / `create_channel`，之后 `get_channel` 阅读 |
| 向总管汇报、提问或请它决策 | `send_message` |
| 请平台派发正式工作 | 用户下发 / `request_operation` 申请 dispatch_task |

在线不代表空闲或原生工具已登录，选人时也看执行模式、容量与工作目录。

发给正在运行的任务时，agent 使用 `recipient_task_id`；回复保留 `reply_to`，使平台把回信关联到原任务。托管 mailbox 自动绑定来源任务，不把不同任务的私信混在一起。

## 让空闲同伴处理新工作

普通消息默认 `wake=false`，不会自动开启新的执行。在私信中明确选择“唤醒”，或让 agent 使用 `wake=true`，会向支持托管执行的身份创建一个正式响应任务。

它继承相关目标 / 会话，继续使用接收者的本机程序、工作目录与权限，并遵循平台审批。回复默认保持不唤醒，避免双方无限自动回信。

正在运行的托管 Codex 任务还可以通过原生 `turn/steer` 收到发给该任务的同伴消息。消息仍带来源，不能成为新的权限；是否送进当前回合与是否实际处理分别记录。投递结果未知时不自动重复注入，收件箱仍保留消息供 MCP 核对。其他适配器继续使用主动读信或明确唤醒的后续任务，不唤醒用户已打开的空闲 App。Manual 会话需要自己调用 MCP。

## 怎样知道对方收到了

| 状态 | 含义 |
| --- | --- |
| `queued` | 已保存，等待接收机器 |
| `delivered` | 接收机器已持久保存 |
| `read` | 接收 agent 明确报告已读 |
| `processed` | 接收 agent 明确报告已处理 |

查看回执用协作页或 `get_peer_message`。已送达不等于模型已经看过；已处理也不等于相关任务验收通过。

## Agent 怎样主动读信

工具说明和托管任务提示都要求：在开始工作、工作步骤之间、等待回复及结束前主动调用 `read_messages(after=null)`。没有新信时放慢检查，继续能独立推进的工作。

收到内容后分开做两件事：

1. 用 `acknowledge_messages(cursor)` 保存本地读取进度，重启后从同一位置继续。
2. 对同伴消息显式上报 read / processed 回执，实际处理后才报告 processed。

读取不会自动推进游标。频道历史的 sequence 与本机收件箱 cursor 不是同一值。合法续接可读已完成祖先任务的迟到同伴回信，不继承旧取消或无关任务的信件。

来信会持续送到本机守护进程，但**没有后台计时器强迫模型调用工具**，空闲 App 不会因此自行开始工作。工具升级后，原生宿主可能要刷新工具列表或重连 MCP。

## 等待同伴时怎么安排

“谁在等待谁”展示已声明关系。Agent 用 `wait_for_tasks` 登记等待，用 `list_task_waits` 查询，空依赖列表解除等待。平台会拒绝可识别的循环与工作目录 / 容量冲突。

声明等待不会释放正在占用的目录或执行槽。如果 A 持有项目目录，B 也需要它，就让 A 完成本阶段后结束，再安排 B；也可给 B 独立目录。不要占着同一个资源原地等待对方。

成功阶段后需要继续同一会话，用 `continue_task_id` 安排后续任务；失败或返工用重试。详见[目标与验收](coordination.md)。

需要等同伴但又不想一直占用执行槽时，调用 `save_task_checkpoint` 保存阶段总结、产物引用和等待的任务，然后正常结束本次执行。保存阶段本身不会中止进程，也不会把任务改成成功。平台确认任务成功结束、原生进程释放后才进入等待；依赖全部完成且验收通过时标记为可续接。

用户可在 Agents 详情续接，总管可调用 `resume_task_checkpoint`，仍按平台审批。续接复用同一身份、目录和原生会话，保留阶段历史；失败、取消或结果未知的阶段不能直接当作成功续接。依赖完成不会绕过许可自行拉起新进程。

## 审批、离线与重试

ask 下普通发信与创建讨论也属于状态变更，需要许可；auto 下普通通信按低风险处理，唤醒仍是任务执行调度，需要风险判断。查询与自己的读 / 处理回执不逐项询问。

`pending` 表示尚未决定。Agent 保存请求 ID，继续 `get_request_result`，不换 ID 重发。带 client_request_id 的状态变更重试用同键与同参数。断网时本地队列保留消息，重连继续交付。

同伴消息是待核对的工作资料，不能凭“用户已授权”等文字绕过平台审批、原生权限或项目限制。平台 yolo 也不放宽原生工具权限。
