# 目标、协作任务与验收

Chiliarch 使用“目标 → 任务 → 验收 → 下一项任务”的持久工作流。用户或总管可以给一个目标保存约束与验收条件，再把实现、测试、评审拆成不同 agent 的任务。执行进程正常结束只表示任务执行完成；总管或用户检查结果后，才使用 `review_task` 明确验收。

## 从目标到交付

1. 使用 `create_goal` 保存标题、目标、约束和验收条件。总管对话中创建的目标关联当前会话；手动创建的目标可由总管协调时建立关联。
2. 使用 `dispatch_task` 指定 agent，并可附带 `goal_id`、`depends_on`、`acceptance_criteria`。没有依赖的任务正常入队；依赖尚未验收的任务保存为 `blocked`，不会发给 agent。
3. agent 回报 `completed`、`failed`、`cancelled`、`expired` 或 `interrupted` 时，平台在保存任务状态的同一事务内记录协调待办。常规进度与心跳不创建模型待办。
4. 总管检查产物，使用 `review_task` 给出 `accepted` 或 `changes_requested`，并记录依据。只有 `completed` 的任务能验收。验收通过会释放后续依赖；反复提交同一结果不会重复派发。
5. 不满足标准时，使用 `retry_task` 创建新尝试。必须填写 `recovery_note`，说明检查了哪些已有产物与实际副作用、为什么可以安全继续；可提供修订后的指令，也可指定另一个 `agent_id` 接手。原任务及其结果、评审、产物完整保留。
6. 所有当前任务都完成且验收通过，且没有相关待处理任务请求或派发审批时，才能将目标改为 `completed`。空目标不能直接完成。

例如：实现任务 A → 测试任务 B（`depends_on=[A]`）→ 评审任务 C（`depends_on=[B]`）。A 只上报执行完成时，B 仍然等待。A 验收通过后，B 才收到派发。如果 A 被要求修改，创建 A 的新尝试；B 继续引用原来的 A，平台沿重试链检查最新尝试，不需要手动修补依赖。

## 在 WebUI 中处理目标

目标列表支持名称、目标说明和任务内容搜索，可组合状态与“仅显示需要处理”筛选。提示按最新尝试判断待验收、返工、依赖、离线、未领取及执行器受阻；历史失败尝试仍可查阅，但不会重复计入当前问题。下级待处理请求及 `resolve_agent_request` 包裹审批关联回所属目标，许可未处理时不会误报可以结束目标。已取消目标仍显示尚未确认停止的任务。

在任务的重试弹窗选择原 agent 或其他未吊销 agent，并填写实际核查及恢复理由；提交失败时保留选择与输入。交接传递执行记录和产物引用，不自动复制本机文件；跨机器材料可显式使用[共享产物](artifacts.md)上传和下载。运行中、取消未确认及已结束目标内的任务不开放重试入口；执行权限和最终参数校验始终由服务端决定。

下发和重试表单支持可选工作目录。填写 agent 机器上的已有绝对路径，目录作为受审批的任务参数持久保存；新任务留空使用 agent 本机默认值，同身份重试优先保留前次实际或指定目录，换 agent 留空使用对方的默认值。会话续接继承原目录，不允许在另一项目中恢复原会话；具体规则见 [默认目录与任务目录](agents/index.md#默认目录与任务目录)。

## 总管与用户使用相同的工具

| 工具 | 用途 | 关键参数 |
| --- | --- | --- |
| `create_goal` | 建立持久目标 | `title`、`objective`、`constraints`、`acceptance_criteria`，可选 `conversation_id` |
| `list_goals` / `get_goal` | 查看目标、全部任务尝试、评审、产物 | `get_goal` 使用 `goal_id` |
| `update_goal` | 修改标题、约束、验收条件、总结与状态 | `goal_id` 与需要修改的字段；状态 `active`、`blocked`、`completed`、`cancelled` |
| `dispatch_task` | 派发或安排等待依赖的任务 | 原有 `agent_id`、`instruction`、`parameters`，可选 `workdir`、`continue_task_id`、`goal_id`、`conversation_id`、`depends_on`、`acceptance_criteria` |
| `review_task` | 明确验收或要求修改 | `task_id`、`decision`、非空 `note`，可选 `artifacts` |
| `retry_task` | 核查实际执行情况后重试或交给其他 agent | `task_id`、非空 `recovery_note`，可选新 `instruction`、接手者 `agent_id`、任务目录 `workdir` |

这些工具均经过 `OperationService` 的参数校验、幂等记录和审批边界。查询不需要审批；`ask` 下状态变更仍需用户批准，`auto` 按风险处理，`yolo` 自主执行。重试属于高风险操作，`auto` 下不能通过模型声明低风险跳过审批。等待依赖的任务在首次派发时已经审批，依赖通过后的出队延续该授权，不再次请求同一许可。

下级 agent 只能提交 `agent.request`，不能直接执行上述管理操作或直接验收自己的结果。总管处理请求仍遵守当前模式。总管也不能批准自己的待审批操作。

## 产物与上下文交接

每个产物引用包含：

```json
{
  "name": "实现提交",
  "uri": "https://github.com/your-org/your-repo/commit/revision",
  "kind": "commit",
  "digest": null
}
```

`name` 与 `uri` 必填，`kind` 默认 `reference`，`digest` 可选。引用可以是提交、PR、报告、共享文件等；支持 HTTP(S)、file、git、ssh、chiliarch 产物引用及本地路径，不接受 javascript/data 等可执行或内嵌内容 URI。URI 不得含内嵌用户名或密码，也不要使用携带私密凭证的 URL。平台记录引用，**不会主动访问 agent 机器或自动下载文件**。`file://` 或本地路径只有能够访问同一文件系统的下游才可使用；跨机器协作应提供实际可访问的仓库地址，或上传产物后使用 `chiliarch:artifact:<ID>`，由接手者调用 `download_artifact` 获取并校验内容。

有目标、验收条件、依赖或重试关系的派发，在 `parameters.chiliarch_context` 内附带目标约束、任务验收条件、最新依赖结果与产物。Codex／Claude runner 将其作为任务数据提供给模型。调用者不能自行覆写这个保留字段；可执行程序、权限及沙箱策略仍由本地原生设置决定。显式 `dispatch_task.workdir` 会作为独立启动字段下发，并在上下文中保留用于查看的目录记录。

重试还附带 `previous_attempt`：其中 `task` 包含上一尝试的 ID、agent、指令、执行状态、结果和错误，另附 `review_status`、`review_note`、`artifacts` 与本次 `recovery_note`。上一尝试的 `parameters` 不递归复制进交接材料，避免多次重试不断膨胀；`retry_of` 指向更早尝试，需要时可继续查询历史。发送前沿用敏感字段脱敏。不同机器不会自动共享工作目录，接手者应根据产物引用取得实际文件，再核对版本与恢复说明。

例如，确认旧任务已中断且核查实际改动后，让另一个 agent 接手：

```json
{
  "task_id": "previous-task-id",
  "agent_id": "replacement-agent-id",
  "instruction": "基于已提交的实现补齐失败的回归测试",
  "recovery_note": "已检查原工作目录和提交，确认原进程停止；复用已有提交，只补缺失测试"
}
```

通过 `retry_task` 提交上述参数，新尝试仍属于同一目标、会话、依赖链和验收条件；依赖旧任务的下游自动检查新尝试。省略 `agent_id` 则继续使用原 agent。接手者必须已配对且未吊销，允许离线排队。原 agent 已吊销不妨碍转交其已确认终态的任务，但吊销凭证本身并不证明任务已停止。等待用户审批期间若接手者被吊销，批准操作会拒绝执行，不会偷偷切换到其他 agent。

验收已通过后不允许再改成“要求修改”，因为后续工作可能已经开始。需要撤回结果时，应取消相关后续工作并建立明确的跟进任务。系统保留历史评审及每次新尝试；验收依据由用户或总管负责判断，系统不会仅凭退出码推断符合业务标准。

## 暂停、取消与恢复

- `blocked` 目标暂停释放尚未派发的任务；已经运行的任务继续回报状态。改回 `active` 会重新检查依赖并释放满足条件的任务。
- 取消目标会取消其所有未完成任务：尚未派发的依赖任务直接取消，已经入队或运行的任务通过原有出站队列发送取消请求。凭证已吊销时保存取消意图及远端执行未知状态，不能证明进程已经停止。相关待派发/重试审批及下级请求同步撤销，避免已取消目标继续等待旧许可。
- 队列容量不足或 agent 凭证被吊销时，满足依赖的任务保留为 `blocked`，维护循环继续核对可派发条件，不丢失已完成的验收。
- 失败、中断、取消、到期或被要求修改的任务可以明确重试。旧尝试已有后继时不能再创建分叉；应操作最新尝试。未知外部副作用绝不自动重放。
- 重试保留原任务的目标、会话、依赖和验收条件，支持用 `agent_id` 将新尝试交给其他 agent；旧尝试的执行归属不变。仍在执行、尚未接收取消确认的任务不能直接转交，也不会因为指定了新 agent 就被强制取消。需要先停止并确认原任务终态、核查实际副作用，再显式重试。同目标内另建普通任务不会替代旧失败任务；应使用重试链表达接手关系。

## 持久化与扩展

原有 `tasks` 表保持兼容，新增三张附加表，由启动时 `create_all` 建立：

- `coordination_goals`：目标、约束、验收条件、状态、协调会话及总结。
- `coordination_task_links`：任务与目标/会话关联、依赖、验收、产物、重试链。普通无目标任务也保存关联元数据，已有旧任务按需补充默认关联。
- `coordination_events`：与业务状态同一事务写入的总管待办，包含唯一 `event_key`、类型、目标/任务/会话、载荷、处理状态、运行 ID 与创建时间。

终态事件使用 `task-terminal:{task_id}` 去重。用户手动修改目标、验收或重试会产生对应协调待办；总管自己的同类工具调用不会额外生成自唤醒事件，避免循环。协调消费者在业务提交后处理待办，并把同一目标的工作聚合到其会话。普通任务进度不触发新的模型轮次。

同一会话的积压协调事件合并成一批，每个目标的当前快照只读取一次，整批待办与模型运行在同一事务绑定；会话忙碌或等待审批时继续保留待办，处理中后来到达的事件进入下一批。下级通过 `metadata.task_id` 带上本任务，平台核验所属 agent 后将来信归并；下级来信仍逐封处理。模型上下文保留完整任务资料，页面显示简短事件说明。未配置模型时先排队。

用户停止总管或不可恢复模型失败后，会话的自动协调和下级来信处理暂停，未处理内容继续排队。临时模型连接、限流及服务错误可按配置退避开启新的核查轮次，重启不重置重试预算；它不会重放旧工具副作用。用户随后发送新消息，或在目标页点击“继续协调”才恢复；普通编辑目标标题不表示恢复，停止前已排队的旧恢复请求也不会重新唤醒会话。停止总管不代表已取消 agent 的工作，需单独核对并取消任务。

重启会为会话最新中断的目标轮次及独立任务协调生成一次恢复待办，先核对当前任务与操作结果，再决定下一步；之后已有停止、失败或成功轮次时，不再复活更旧的中断。整批中断及恢复期间新增的关联任务仍可核对。已完成、仍运行或结果未知的外部工作不会因为恢复而直接重新执行；明确的 `retry_task` 仍受审批及核查理由约束。服务重启不会自行恢复原生 Codex/Claude 的中断工作；显式 `dispatch_task(continue_task_id=...)` 仅允许续接最近成功且已确认停止的受管会话，网络恢复不代表未知副作用已核实。运行中或等待审批的会话需要先停止；关联目标仍 active/blocked 时不能删除会话历史。

`/api/state` 增加 `goals` 与 `task_links`。`get_goal` / `list_goals` 的目标对象另含 `tasks`、`task_links`、`artifacts`，保留所有历史尝试供审计。`get_task` 同时返回 `task_link`。

这是一套单实例持久协调机制，提供经出站连接的[共享产物](artifacts.md)，尚未提供自动合并代码、自动证明测试结论或分布式调度租约。部署和连接方式仍遵守 [协议](protocol.md) 与 [守护进程](daemon.md) 的出站连接要求。

## 同伴协作与等待

agent 可通过私信显式唤醒同伴处理，生成的正式任务继承所属目标，执行完成后仍需验收。使用 `wait_for_tasks` 声明等待关系，平台拒绝循环依赖及已知工作目录/执行容量造成的相互等待；声明不释放原生进程或目录锁。同目录合作应先结束一个阶段再续轮，或分别使用独立目录。`continue_task_id` 用于成功工作后的新一轮，`retry_task` 用于失败或返工，两者不可互换。详见[横向通信与协作](collaboration.md)。
