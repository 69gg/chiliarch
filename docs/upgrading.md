# 升级 Chiliarch

平台服务器与每台 agent 机器分别升级。升级 Chiliarch 不会升级 Codex、Claude Code 或 OpenCode，也不要求重新配对或重新 init。

## 默认自动更新

标准 `uv tool install chiliarch` 安装，默认在**启动服务时**检查符合当前 Python 和原安装约束的正式新版。

- 平台：`chiliarch serve`。
- Agent 机器：守护进程启动、登录自启动，以及需要启动服务的安装 / 接入命令。
- 独立连接模式：MCP 或 runner 进程启动。

帮助、版本查询和状态检查不检查 PyPI；普通 MCP 工具调用也不检查。运行中的服务不定时替换自己，新版本在相应进程下一次启动时生效。

更新在后台静默检查、下载并安装到独立运行环境，校验后选择它启动，保留旧环境。Windows 的守护进程自启动、更新安装及版本交接均不创建控制台窗口；macOS 和 Linux 继续使用各自的后台用户服务。断网、下载或校验失败时继续用上一份可用版本，原因写入更新日志。

检查仍发生在服务启动阶段，新版准备好后才启动服务；不会在运行任务时替换进程。你主动运行的 `serve` 或 `daemon run` 仍是前台命令，不会替你关闭终端。

## 怎样应用新版

平台先正常停止，再用原 `serve` 命令启动，继续读取原配置和数据库。

Agent 机器已有健康、接口兼容的 daemon 会被复用。新增 agent 或 CLI 检查到新版不会强停它；需要应用新版时，先等本机全部托管任务结束，再运行：

```sh
chiliarch daemon restart
chiliarch daemon status
```

独立守护目录继续带原 `--directory`。重启影响它管理的所有身份和任务，不只当前 agent。

## 手动升级

希望手动更新工具环境时：

```sh
uv tool upgrade chiliarch
chiliarch --version
```

先排空任务并正常停止需要升级的服务，然后按原来的命令重新启动。平台和 agent 机器都分别执行，不会由服务器远程替另一台机器更新。

Windows 已有的 Chiliarch 登录任务会在新版启动时自动更新为无窗口方式，保留目录、原生配置环境和启用／禁用状态，不需要卸载重装。如果升级是由旧启动项触发的，当次旧版已经打开的窗口可能仍在；等任务空闲后再执行一次 `chiliarch daemon restart`，之后登录自启动会保持后台运行。

自行创建的系统服务不由 Chiliarch 接管。如果手动移动了安装环境、旧入口已无法执行，按[服务环境维护](daemon.md#原生配置目录与环境)修复启动项，保留原登记和状态库。不要为升级重新配对。

## 新功能和配置会怎样更新

新版启动时会检查已有配置，自动补入缺少的字段，并使用新版定义的默认值。例如旧 `chiliarch.toml` 没有 `[github]`，会补入 `enabled = true`；如果你已经设置 `enabled = false`，则继续保持关闭。

平台 TOML 在加载与热重载时补全，守护进程的 `daemon.json` 在启动保存时补全。密码、API Key、端口、工作目录和身份登记等已有值继续保留，环境变量覆盖仍只对运行时生效。无需再次 init、配对或重新安装启动项。

补全 TOML 时会统一文件格式，原有注释不会保留；完整配置不会重复写入。配置只读时，程序仍在内存中使用缺失项的默认值，并记录未能保存的提示。无效配置不会被自动修正或覆盖，也不会凭空创建尚未初始化的平台配置。

## 固定版本和安装来源

固定版本的安装会继续保留约束。例如 `chiliarch==0.4.4` 不会自动跳到其他版本，范围约束也只在范围内升级。需要改变约束时，显式重新安装所需版本或范围。

源码、editable、Git / URL 安装，以及无法确认来源的安装，不会被自动替换。自定义镜像或复杂 constraints / overrides 无法按原语义复用时，会在更新日志中提示手动更新，不改成另一来源。自动更新排除预发布、开发版、撤回和不兼容当前 Python 的发行文件。

更多工具环境说明见 [uv 工具升级指南](https://docs.astral.sh/uv/guides/tools/#upgrading-tools)。

## 关闭自动更新

在**实际启动进程的环境**设置 `CHILIARCH_AUTO_UPDATE=0`。

Linux / macOS 当前终端：

```sh
CHILIARCH_AUTO_UPDATE=0 chiliarch serve
```

Windows PowerShell 当前终端：

```powershell
$env:CHILIARCH_AUTO_UPDATE = '0'
chiliarch serve
```

删除变量或改为 `1` 恢复默认行为。关闭检查仍使用之前已选中的运行版本，不是降级命令。

系统服务需要在它的启动环境设置；终端改变量不会改变已运行的服务。Chiliarch 管理的 daemon 保存安装时的环境，已有启动项需等任务空闲后，在设置了变量的终端卸载并重新安装。详见[守护进程环境](daemon.md#原生配置目录与环境)。

此开关不属于平台 TOML 或热重载设置。`transport.upgrade_interval_seconds` 只是重新尝试 WS 的间隔，与软件版本更新无关。

## 运行环境与更新日志

数据位于用户 Chiliarch 状态根的 `updates/<安装标识>/`。`runtimes` 保存独立版本环境，`active.json` 保存已通过校验的选择，同一 uv 工具安装共用它们；独立 daemon 目录不会另建一套。

`chiliarch --version` 显示 CLI 实际选中的版本，`daemon status` 显示已运行服务的版本。`uv tool list` 可能仍显示外层工具环境原版本，三者暂时不同不一定是失败。

更新情况仅写该目录的 `update.log`，不会向终端或 MCP 管道打印更新提示。日志按 1 MiB 轮换，保留 2 份备份。旧运行环境不自动删除，避免损坏仍运行的进程或自启动项路径。

第一次启动遇到更新可能等待下载与安装。版本查询超时为 5 秒，环境创建、安装与校验各有期限；失败继续原版本。不要在正在使用时手动删除运行环境。

## 更新前保留什么

通常升级保留配置、数据库、登记、凭证和原生设置。重要部署仍建议保存[平台数据库快照](deployment.md#备份与恢复)，同时备份 TOML、必要环境、守护目录和各身份状态文件。

程序能保留旧运行环境，不代表未来数据库迁移后一定能直接降级读取同一库。需要恢复时使用匹配的版本与备份。

| 情况 | 处理 |
| --- | --- |
| 下载失败但旧版可用 | 核对 uv 与网络，下一次启动会再检查 |
| CLI 新、daemon 旧 | 空闲后 restart，先核对本地 API 是否兼容 |
| 自动更新没有跨越固定版本 | 保留约束是预期行为；显式更改安装约束 |
| 新终端能找到原生工具，daemon 找不到 | 刷新服务保存的 PATH / 配置目录环境 |
| 升级后当前宿主还是旧工具说明 | 刷新工具列表、重连 MCP 或开新会话 |
