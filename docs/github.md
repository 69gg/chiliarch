# 用多个 agents 完成 GitHub 项目

你可以把一个 GitHub 仓库登记成 Chiliarch 项目，让不同机器上的 agents 分工开发、交付 PR、互相评审、跟进 CI，再按项目规则合并和发布。总管 AI 和“项目”页面使用同一套操作。

## 开始前需要什么

- 平台已经启动，至少一个 agent 已经通过本机守护进程接入。
- 执行工作的机器安装了 Git 和 GitHub CLI（`gh`），并已登录能访问该仓库的账号。多个机器可以使用同一个账号。
- Git 的提交姓名、邮箱和需要的签名设置已经配置。Chiliarch 继承它们，不会偷偷改全局 Git 设置或关闭签名。

平台服务器不需要保存 GitHub token。仓库操作由 agent 所在机器的守护进程执行；它仍然主动连接平台，机器不用开放端口。

`gh` 登录成功、Git 能推送、签名密钥可用是三件不同的事。节点探测会显示已观察到的信息；没有实际验证过的推送和签名能力会保留“未验证”。

## 第一次登记项目

1. 打开“项目”，登记仓库（`owner/name`）、GitHub 主机和目标分支。目标分支填写仓库实际使用的分支。
2. 绑定一个已配对的 agent，运行仓库探测。平台会记录仓库 ID、账号、权限、Git/gh 版本和本机 Git 设置。
3. 默认留空已有仓库路径。守护进程会在自己的数据目录中准备专用副本，为每次工作创建独立 worktree。
4. 如果要复用已有仓库，显式填写该机器上的绝对路径。Chiliarch 创建额外 worktree，不切换你当前的分支，不覆盖未提交文件。
5. 设置需要通过的 CI 检查名称、是否必须独立评审、是否要求签名和允许的合并方式。

也可以直接告诉总管：“登记这个仓库，绑定这几个 agents，先检查环境，然后列出还缺什么。”

## 下发工作与分支

一个工作项代表要完成的事情；一次执行尝试代表某个 agent 在某条分支上的一次具体执行。返工或换人保留旧尝试，不覆盖历史。

创建工作项时选择一种交付方式：

| 方式 | 适合的情况 | 交付过程 |
| --- | --- | --- |
| 分别交付 | 各项改动可以独立合并 | 各任务 PR 合入项目目标分支 |
| 目标集成 | 多项改动要一起交付 | 子任务 PR 合入目标集成分支，再创建总 PR |

同一目标的方式保持一致。依赖其他工作项时，后者必须已经合并；开始工作前，守护进程核对给定基线确实包含依赖提交。填写的是完整 commit SHA，不能把一个随时变化的分支名当作精确基线。

平台先准备目录与分支，成功后才启动 agent。你能看到 `work_item_id → attempt_id → task_id` 的关联，以及目录、基线和交付分支。默认分支前缀是 `chiliarch`，可以在项目策略中配置。

## 从修改到 PR

原生 agent 编辑和运行自己的检查。它可以通过 MCP 给同伴发消息、查询共享事实、汇报阻塞，并向总管申请下一步。

文件修改结束、原生任务确认停止后，再执行交付。交付工具核对工作区归属与分支，按本机 Git 设置提交、推送，并创建或找到对应的 PR。已创建的 PR 会按仓库、head/base 和操作记录核对，不会因为网络重试重复创建。

交付与运行中的编辑任务不能抢占同一工作区。托管 agent 完成编辑后，应结束当前工作并向总管交接；不要在自己仍占用目录时等待一次必须等目录释放才能执行的交付请求。

## 评审、CI 与合并

评审由另一个 agent 完成，记录具体 head SHA、base SHA、结论与证据。所有 agents 使用同一个 GitHub 账号时，Chiliarch 会保存独立 agent 的身份，并用明确署名的 GitHub 评论同步结论；这不等于 GitHub 原生的另一个账号批准。

配置了必需 CI 后，缺少结果、排队中、失败或查询失败都不能算通过。改了 head 或 base，需要针对新版本重新核对评审与检查。总集成 PR 也要单独验证，子任务通过不能替代组合验证。

合并前再次检查实际 head/base，提交预期 head SHA，遵守仓库保护规则。不使用管理员绕过选项。平台串行处理自己的合并请求，外部人员仍然可能改动目标分支，因此基线变化会阻止沿用旧证据。

审批方式继续沿用平台模式：

- `ask`：总管或下级发起的状态变更需要用户批准。
- `auto`：按风险和项目规则决定；允许自动合并需要项目显式开启。
- `yolo`：平台内自主执行，但仍要通过项目验收门槛和 GitHub 仓库规则。

## 发布一个版本

发布需要单独开启项目的发布能力，不会因为允许合并就自动获得发布意图。

在项目发布配置中登记仓库实际使用的版本命令、变更日志来源、tag 模板、工作流和 Release 创建方。必须把 `verify_command` 指向一个已登记的验证命令，用它检查指定版本、变更日志和发布就绪状态；未配置或验证失败时不打 tag。命令使用参数数组，例如 `["uv", "run", "python", "scripts/bump_version.py", "0.5.0"]`，复用仓库自己的脚本；平台不会猜测每个项目的版本文件。

先完成版本与变更日志修改，并按正常交付流程验证和合并。发布时指定已经核对的提交与版本，再跟进发布工作流和 Release。tag 已存在时只接受同一提交，不会移动或覆盖已经发布的 tag。

Release 的创建方只能有一个：若工作流负责创建，守护进程只观察；若选择守护进程创建，工作流不要重复创建。同样，“tag 推送成功”不等于“包已发布成功”，要查看项目配置的发布结果。

## 共享事实与选人

项目事实用来保存需求、接口约定和决定，同时记录来源与版本。工作项声明自己使用的版本；事实变更会标记受影响的工作，要求重新核对。更新使用预期版本号，避免两名 agents 静默覆盖彼此的决定。

总管可以查询节点建议：是否在线、OS 是否符合、是否具备声明的能力、是否支持仓库命令与独立目录、是否有空闲容量、仓库身份是否探测过。建议会带原因，不会仅因为 agent 名称看起来合适就派任务。

项目时间线将工作项、执行、命令、PR、评审和事实串起来。用量只统计原生工具实际报告的数据；没有报告的用量显示未知，不视为零，也不当作服务商账单。

## 从已有 Issue 开始

在项目页填写 Issue 编号，先查看原文，再选择导入目标。同一个 Issue 重复导入会复用已有目标。通过项目工具发布进度评论、更新 open/closed 或标签时仍按模式审批；这些操作使用节点的 GitHub 身份。

## 自动处理 GitHub 事件

只有显式配置的规则才会创建目标。规则包含事件类型、允许触发的 GitHub 账号，以及标签或评论指令条件。普通 issue 或评论不会默认启动 agents。

节点通过出站连接执行事件查询；事件按规则和 GitHub 事件 ID 去重。规则创建的是有来源的目标，后续分配与执行继续遵守平台策略。Issue/评论正文是待处理资料，不能让其中的文字覆盖平台权限。

首次观察只读取最近一页；后续会逐页找到上次的位置，最多覆盖 GitHub 提供的 300 条事件。GitHub 还会移除超过 30 天的事件，因此长时间离线或短时间活动过多时，历史可能不完整。找不到上次位置时平台会提示事件缺口并保留原位置，不会宣称已经全部同步；请核对遗漏的 Issue／PR，再明确重设观察位置。

## 遇到等待、失败或失联

| 显示的状态 | 含义与处理 |
| --- | --- |
| pending | 命令已登记，可能正在等节点或执行；继续查同一个命令 ID |
| completed | 已收到该命令的结果；仍需区分这是探测、推送还是整个发布完成 |
| failed | 已知失败；查看原因，修正环境或输入后再决定下一步 |
| unknown | 外部操作可能已发生；先执行核对，不能换一个 ID 重做 |

消息已 ACK 只表示持久接收。机器失联不等于进程停止；换人前先确认旧进程和外部副作用，填写恢复说明。过期尝试的晚到结果保留为历史，不覆盖新的工作。

同账号是便捷部署方式，不提供 GitHub 账号级隔离。如果原生 agent 自己能运行 git/gh，它也可能在平台流程之外操作仓库；需要更强隔离时，应使用不同身份和执行环境。

## Agent 如何调用

MCP 的 `project_tools` 返回当前项目工具的完整 schema、说明和风险等级。之后通过 `request_operation` 调用；使用稳定的 `client_request_id`，保存 `request_id` 与返回的 `command.id`。

请求仍在等待审批时查 `get_request_result`；已经排队的仓库命令查 `get_project_command`；结果未知时调用 `reconcile_project_command`。不要重复创建请求、不要把 pending 当作授权，也不要绕过原生许可。

完整通信说明见 [Agent 工具](agents/tools.md)，底层消息结构见 [协议](protocol.md)。
